# Шаблон правил AI-разработки

Версия: **0.1.0**. Переносимая основа для совместной разработки с AI:
короткие общие правила, контекст конкретного проекта и подключаемые процедуры.
Ядро не зависит от языка программирования, облака, модели или редактора.
Автоматическая загрузка и технические ограничения зависят от выбранного инструмента.

## Начало работы в другом проекте

1. Сопоставь существующие инструкции целевого репозитория с шаблоном. Не заменяй
   их вслепую: сохрани проектные ограничения, устрани противоречия с владельцем.
2. Перенеси ядро, паспорт, каталоги rules и templates с сохранением структуры.
   Прочие каталоги подключай по необходимости. Не переноси архив.
3. Заполни паспорт: реальные команды, архитектуру, критерии успеха, владельцев
   решений, права и бюджеты. Для неприменимых полей укажи `N/A` с причиной.
   После ручной проверки замени статус `template` на `configured`.
4. Выбери способ загрузки из руководства адаптеров. Не подключай одинаковые
   инструкции несколькими независимыми копиями.
5. Настрой необходимые технические ограничения. Запиши, что реально проверено,
   а что остаётся только инструкцией. Отсутствие CI не означает успешный gate.
6. В новой сессии проверь загрузку файлов и пройди применимые eval-сценарии.
   Зафиксируй версии инструмента, модели и правил, результаты и исключения.
7. Начни с небольшой задачи. Полный цикл и автоматизацию добавляй по риску,
   не делай все возможные механизмы обязательными для каждого проекта.

В паспорте намеренно нет вымышленных команд и предписанного стека. Незаполненные
поля не мешают обсуждать или развивать сам шаблон, но не разрешают агенту угадывать
конфигурацию целевого продукта. Готовность паспорта проверяет человек.

## Работа над этим шаблоном

Нужен Node.js 18+ только для структурной проверки; для использования Markdown
Node.js не требуется. Нет npm-зависимостей, установки пакетов и сетевых вызовов.
Из корня этого репозитория выполни:

```text
node tools/validate.mjs
node tools/validate.mjs --self-test
```

Обе команды должны завершиться с exit code 0 и сообщением `PASS`.
Первая проверяет обязательные файлы, простые относительные ссылки на Markdown,
закрытие тройных backtick-блоков, символы повреждения UTF-8 и лимит ядра в 60 строк.
Вторая проверяет валидатор на корректном примере и семи негативных случаях.
Архив исключён. Это намеренно ограниченная структурная проверка, не универсальный
Markdown-парсер: она не проверяет URL, anchors, все виды ссылок, смысл правил,
готовность паспорта, загрузку адаптеров или соблюдение инструкций моделью.

После изменений в правилах, адаптере или модели также пройди применимые
[поведенческие проверки](evals/README.md). Для публикации версии нужны обе
структурные команды и рассмотрение поведенческого отчёта человеком.
Коммит и публикация выполняются только с отдельного разрешения.

## Как менять и переиспользовать

Для нового правила сначала опиши конкретный повторяемый сбой, область действия,
проверяемое требование, причину и владельца. Повторная ошибка служит поводом
предложить правило, но не автоматическим разрешением переписать инструкции.

- Обязательное для большинства задач помещай в ядро, сохраняя его коротким.
- Факт о конкретном проекте помещай в паспорт или связанный предметный документ.
- Повторяемую процедуру оформляй как skill, подключаемый по задаче.
- Необходи́мый запрет обеспечивай техническим контролем и проверяй его границы.
- Добавляй сценарий, способный обнаружить исходный сбой; удаляй устаревшие правила.

Обновляй CHANGELOG и версию паспорта при выпуске. В v0.x изменение обязательного
процесса повышает minor; исправление текста без изменения поведения повышает patch.
При переносе обновления сравни три версии: исходную версию шаблона, новый шаблон
и локально изменённый экземпляр. Переноси выбранные изменения через ревью;
не перезаписывай заполненный паспорт и локальные правила. Запиши базовую версию
и местные отличия, затем повтори структурные и поведенческие проверки.

## Основание и адаптация

Основано на [The AI-native SDLC playbook](https://claude.com/blog/the-ai-native-sdlc-playbook):
артефакты между этапами, короткий контекст, skills, обратная связь, технические
gates, ответственность человека и улучшение правил по результатам эксплуатации.

Наша адаптация: общее Markdown-ядро, сокращённый путь для простых задач,
необязательные интеграции вместо корпоративной инфраструктуры по умолчанию.
Автономный deploy, агенты по расписанию, платные eval-запуски и hooks не установлены.
