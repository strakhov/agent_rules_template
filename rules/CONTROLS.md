# Полномочия и технический контроль

Читать перед действиями с данными, доступами, внешними системами и релизами.
Конкретные разрешения и ответственные задаются в [PROJECT.md](../PROJECT.md).
Эта политика сама по себе ничего технически не блокирует.

## Разрешения по умолчанию

| Действие | Условие |
| --- | --- |
| Чтение обычного кода и локальные проверки | В рамках задачи; без передачи данных, оплаты и разрушительных эффектов |
| Локальные изменения кода и тестов | Запрошена реализация; для полного режима принят план |
| Установка пакетов, сетевые и платные вызовы | Разрешены в паспорте или отдельно; известны источник, эффекты и бюджет |
| Изменение API, миграции, конфигурация инфраструктуры | Оценены совместимость, данные, откат; получено явное разрешение |
| Коммит, push, создание PR, merge | Явно разрешены соответствующие действия; план реализации не равен разрешению на merge |
| Production, удаление данных, изменение доступов | Разрешение на конкретную цель и действие; проверенный путь восстановления |
| Ослабление правил, CI, sandbox, проверок безопасности | Отдельная задача и одобрение владельца; не способ разблокировать текущую работу |

Разрешение на dev не распространяется на staging или production. Разрешение
на код не разрешает расходы. Для повторов внешних вызовов нужны лимит и проверка
идемпотентности; после неопределённого ответа сначала выясни состояние операции.

## Что обеспечивать технически

| Требование | Возможный механизм | Как проверить |
| --- | --- | --- |
| Защищённые пути | Права доступа, sandbox, hook до записи | Безопасная попытка записи в фикстуру отклоняется |
| Нет прямого merge | Branch protection и ограниченный токен | Тестовый аккаунт без роли не может обойти PR |
| Нет утечки секретов | Secret scanning, изоляция файлов, ограничение сети | Синтетический маркер обнаружен; запрещённый маршрут закрыт |
| Проверки перед merge | Required checks в CI | Намеренно падающий тест в тестовом PR блокирует merge |
| Согласование релиза | Deployment environment approvals | Тестовый релиз без одобрения не проходит gate |
| Защита принятого регрессионного теста | Проверка diff или hook фазы bugfix | Изменение утверждённой проверки требует отдельного решения |

Не проверяй защиту на реальных секретах или production. Используй изолированный
стенд и явно разрешённые тестовые операции. Hook покрывает только события своего
инструмента; он не заменяет права ОС, sandbox, защиту ветки и CI. Поиск слова
`production` в shell-команде не является надёжной границей безопасности.

В v0.1.0 технические ограничения не установлены. В целевом проекте запиши
для каждого обязательного контроля: владельца, реализацию, проверку, свидетельство
результата и известные обходные пути. Непроверенный контроль не считай действующим.

## Выпуск и эксплуатация

Перед релизом нужны применимые проверки, одобрение нужной версии, область выпуска,
наблюдаемые критерии здоровья и проверенный сценарий отката. При необратимых
изменениях данных нужен отдельный план восстановления. Не обещай простой rollback.

Автоматический мониторинг должен иметь измеримый порог и ограниченные действия:
запись события, read-only диагностика, предложение PR, заранее одобренный runbook.
Произвольные пороги не подходят всем метрикам; владелец выбирает их по baseline.
Наблюдение запускает диагностику, но не доказывает причину и не разрешает релиз.
После инцидента сохрани доказательства, исправление и регрессионную проверку;
повторяемый сбой процесса добавь в набор проверок правил.
